    提示工程

    使用OpenAI API时，你可以通过大型语言模型根据提示生成文本，就像使用ChatGPT一样。模型可以生成几乎任何类型的文本响应——例如代码、数学公式、结构化的JSON数据或类似人类的散文。

    我们的一些官方SDK为了方便起见，在模型响应中包含了一个output_text属性，该属性将模型的所有文本输出聚合为单个字符串。这可以作为访问模型文本输出的快捷方式，可能很有用。

    除了纯文本，你还可以让模型以JSON格式返回结构化数据——此功能称为结构化输出。

    选择模型

    通过API生成内容时，一个关键选择是使用哪个模型——上述代码示例中的model参数。你可以在此处找到可用模型的完整列表。以下是选择文本生成模型时需要考虑的几个因素。

    • 推理模型 会生成内部思维链来分析输入提示，擅长理解复杂任务和多步骤规划。但它们通常比GPT模型更慢、更昂贵。
    • GPT模型 快速、成本效益高且高度智能，但需要更明确的指令来说明如何完成任务。
    • 大型和小型（mini或nano）模型 在速度、成本和智能性之间提供权衡。大型模型在理解提示和跨领域解决问题方面更有效，而小型模型通常更快、更便宜。

    如果不确定，gpt-5.5 为通用文本生成和提示迭代提供了一个强大的默认选择。

    提示工程

    提示工程 是为模型编写有效指令的过程，以便模型能够一致地生成满足你要求的内容。

    由于模型生成的内容是非确定性的，通过提示获得所需输出既是艺术也是科学。然而，你可以应用技术和最佳实践来持续获得良好的结果。

    一些提示工程技术适用于所有模型，例如使用消息角色。但不同类型的模型（如推理模型与GPT模型）可能需要不同的提示方式才能产生最佳结果。即使是同一系列中不同快照的模型也可能产生不同的结果。因此，在构建更复杂的应用时，我们强烈建议：

    • 将你的生产应用固定到特定的模型快照（例如 gpt-4.1-2025-04-14），以确保行为一致。
    • 构建评估（evals）来衡量提示的行为，以便在迭代或更改和升级模型版本时监控提示性能。

    现在，让我们探讨一些可用于构建提示的工具和技术。

    消息角色与指令遵循

    你可以使用instructions API参数或消息角色，以不同级别的权威向模型提供指令。

    instructions参数向模型提供关于其在生成响应时应如何行为的高级指令，包括语气、目标和正确响应的示例。以这种方式提供的任何指令都将优先于input参数中的提示。

    • user消息提供输入和配置，developer消息指令将应用于这些输入和配置，就像函数的参数一样。

    可复用提示

    在OpenAI仪表板中，你可以开发可复用的提示，并在API请求中使用它们，而不是在代码中指定提示的内容。这样，你可以更轻松地构建和评估提示，并在不更改集成代码的情况下部署改进版的提示。

    工作原理如下：

    1. 创建可复用提示 在仪表板中，使用占位符如 {{customer_name}}。
    2. 在API请求中使用提示 使用 prompt 参数。prompt 参数对象有三个可配置的属性：
      • id — 提示的唯一标识符，在仪表板中找到。
      • version — 提示的特定版本（默认为仪表板中指定的“当前”版本）。
      • variables — 要替换提示中变量的值映射。替换值可以是字符串，也可以是其他响应输入消息类型，如 input_image 或 input_file。请参阅完整的API参考。

    使用Markdown和XML格式化消息

    在编写developer和user消息时，你可以结合使用Markdown格式和XML标签，帮助模型理解提示和上下文数据的逻辑边界。

    Markdown标题和列表有助于标记提示的不同部分，并向模型传达层次结构。它们也可能在开发过程中使提示更易读。XML标签有助于界定一段内容（例如用作参考的支持文档）的开始和结束位置。XML属性还可用于定义提示中内容的元数据，这些元数据可以被你的指令引用。

    通常，一条developer消息将包含以下部分，通常按此顺序（但确切的最佳内容和顺序可能因你使用的模型而异）：

    • 身份： 描述助手的目的、沟通风格和高级目标。
    • 指令： 为模型提供关于如何生成所需响应的指导。它应遵循哪些规则？模型应该做什么，绝对不应该做什么？此部分可能包含与你的用例相关的许多子部分，例如模型应如何调用自定义函数。
    • 示例： 提供可能的输入示例，以及模型所需的输出。
    • 上下文： 为模型提供生成响应可能需要的任何额外信息，例如训练数据之外的私密/专有数据，或你知道将特别相关的任何其他数据。此内容通常最好放在提示的末尾附近，因为你可能为不同的生成请求包含不同的上下文。

    通过提示缓存节省成本和延迟

    在构建消息时，你应该尝试将期望在API请求中反复使用的内容放在提示的开头，以及放在JSON请求体中传递给聊天补全或响应式API的最早的API参数中。这可以使你通过提示缓存获得最大的成本和延迟节省。

    少样本学习

    少样本学习允许你通过在提示中包含少量输入/输出示例来引导大型语言模型执行新任务，而不是对模型进行微调。模型会隐式地从这些示例中“学习”模式，并将其应用于提示。提供示例时，尝试展示各种可能的输入及其所需的输出。

    包含相关上下文信息

    在你给模型的提示中包含模型可以用来生成响应的额外上下文信息通常很有用。这样做有几个常见原因：

    • 让模型访问专有数据，或模型训练数据集之外的任何其他数据。
    • 将模型的响应限制在你已确定最有益的一组特定资源。

    将额外相关上下文添加到模型生成请求中的技术有时称为检索增强生成（RAG）。你可以通过多种方式向提示中添加额外上下文，例如查询向量数据库并将返回的文本包含到提示中，或者使用OpenAI内置的文件搜索工具根据上传的文档生成内容。

    规划上下文窗口

    模型在生成请求期间考虑的上下文只能处理有限的数据量。这个内存限制称为上下文窗口，以tokens（令牌）（你传入的数据块，从文本到图像）来定义。

    模型的上下文窗口大小各不相同，从低端的10万令牌到较新GPT-4.1模型的100万令牌。请参阅模型文档了解每个模型的具体上下文窗口大小。

    最新GPT-5系列模型的提示最佳实践

    有关完整的当前处理方法，请使用提示指南。以下实用提醒仍然适用。

    编程

    在提示gpt-5.5进行编程任务时，遵循几个最佳实践最为有效：定义代理的角色，通过示例强制结构化工具使用，要求进行彻底的测试以确保正确性，并设置Markdown标准以产生清晰的输出。

    明确的角色和工作流程指导
    将模型构建为具有明确职责的软件工程代理。为使用functions.run等工具执行代码任务提供清晰的指令，并指定何时不使用某些模式——例如，除非必要，否则避免交互式执行。

    测试和验证
    指导模型使用单元测试或Python命令测试更改，并小心验证补丁，因为像apply_patch这样的工具即使失败也可能返回“完成”。

    工具使用示例
    包含如何使用提供函数调用命令的具体示例，这可以提高可靠性并确保遵守预期的工作流程。

    Markdown标准
    指导模型使用行内代码、代码围栏、列表和适当的表格生成干净、语义正确的markdown，并使用反引号格式化文件路径、函数和类。

    有关特定于编程的详细指导和提示示例，请参阅我们的提示指南。

    代理任务

    对于使用gpt-5.5的代理和长时间运行的任务，将提示集中在三个核心实践上：彻底规划任务以确保完全解决问题，为主要工具使用决策提供清晰的序言，并使用TODO工具以有序的方式跟踪工作流程和进度。

    规划和持久性

    为推理模型设计提示

    在提示推理模型与提示GPT模型时，需要考虑一些差异。一般来说，推理模型在仅提供高级指导的任务上会提供更好的结果。这与GPT模型不同，后者受益于非常精确的指令。

    你可以这样理解推理模型和GPT模型之间的区别：

    • 推理模型就像一位资深同事。你可以给他们一个要实现的目标，并相信他们会自行解决细节问题。
    • GPT模型就像一位初级同事。他们在收到明确的指令以创建特定输出时表现最佳。
